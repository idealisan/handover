# 06 待验证问题与后续分析计划

> 本系列报告全部基于静态分析。下面列出尚未确认的点，以及在不删除任何文件的前提下
> 可以继续做的分析。所有中间产物统一放在 `tmp/analysis/`。

## 1. 待验证问题清单

| # | 问题 | 已有线索 | 需要的验证 |
| --- | --- | --- | --- |
| 1 | SSP 帧头的**精确字节布局**（magic、版本号、长度字段字节序、session_id 宽度、flags 含义） | Mac 有 `hasHeader`、`totalBodyLength`、`lenData`、`readDataToLength:`；APK 有 `SspPacket`、`SspReader` | 抓包 + 反编译 `SspReader` / `SSPRequestOperation` |
| 2 | `enckey` / `derived_key` 的**生成与派生算法**，以及它们是否用于逐帧加密 | proto 第 1/2 轮握手字段；Mac `Failed to create RSA`、`keySize==128`、`data signing failed!`；APK `RSA/ECB/PKCS1Padding`、`SHA256withRSA`、`derivedKey` | 动态 hook 或反汇编密钥交换路径 |
| 3 | 握手成功判定 `base64(RSA_encrypt('ok'))` 中，**密钥对由谁生成、公钥如何随 `enckey` 传递** | proto 注释；Mac `enckey` + `md5`；APK `writeKeyExchangeInfo====rsaResultStr===` | 反汇编 + 运行时观察 |
| 4 | APK `parseIoBuffer` 里硬编码 AES-256-CBC key/IV 解密的**到底是哪一层数据**（全部帧？仅密钥材料？） | `main/jni/smartfolder.c` 源码；dex 中 `parseIoBuffer` | 动态调用 hook 或对比收发字节 |
| 5 | Wi-Fi 模式下**谁是服务端**：手机 `ServerSocket` 与电脑 `socket:didAcceptNewSocket:` 都存在的含义 | 两端都有 publish/browse/listen | 抓包看 TCP SYN 方向与 NSD TXT 记录 |
| 6 | TLS 是否默认启用、自签证书如何校验 | `GCDAsyncSocketManuallyEvaluateTrust`、SSL 错误串、`NSAllowsArbitraryLoads=true`、APK `cleartextTrafficPermitted=true` | 抓包看是否有 TLS 握手 |
| 7 | 二维码**载荷的具体编码**（IP:port？含 UUID/指纹/临时公钥？） | `IPPortQRCode`、`refresh qrcode then relisten ip port %@`、`didScanQRCode IP : %@`、`APKQRCode` | 生成二维码并解码；反编译二维码生成逻辑 |
| 8 | USB 三条子路径（AOA / ADB / Wi-Fi）的**优先级与自动切换策略** | UI「建议使用 USB 数据线连接」「connect device error reason (AOA)」、AOA 与 ADB 各有独立错误文案 | 实机插拔观察日志 |
| 9 | `tcp:10086` / `tcp:19999` 是否分别为 SSP 与音频 HTTP 服务端口 | Mac 有两组 forward 正则与 `audioHttpServerSocketPort`；`http://127.0.0.1:%lu/?file_path=%@` | 抓包 / 运行时端口检查 |
| 10 | `session_id` 的生成规则、裸二进制流与 HTTP 文件通道的**分工** | proto 两处「session_id + binary」注释；`&clientSessionId=`、`downloadFile register sessionId =` | 抓包与反编译 `SspFileTransferTask` |
| 11 | 心跳间隔、`heartbeat_timeout_second` 的实际取值 | proto 字段、Mac `HeartBeat timeout, client dead`、`keepAliveOperationQueue` | 运行时日志 |
| 12 | 官方手机端 APK 是否同样带 `main/proto` 与 native AES 混淆 | 本样本是第三方重打包实现 | 找到官方原版 APK 做对照（静态比对 proto 是否一致） |
| 13 | 目录监控、照片自动同步在**断线重连后**的续传语义 | `PHOTO_SYNC_REQUEST` 带上次快照；UI「下次连接时会继续同步」 | 运行时构造断线场景 |

## 2. 可以继续做的静态分析（无需运行程序）

- 对 `SmartFinderCore` / `HandShakerComponent` 用 `otool -o` / `otool -ov` 导出 Objective-C
  类、方法、ivar 与协议列表，比 `strings` 更结构化。
- 用 `nm -m` / `nm -U` 查看导出符号与未定义符号，确认 OpenSSL、libusb、protobuf 的链接方式。
- 若后续能安装 `class-dump`、`jadx`、`apktool`、`baksmali`，可以：
  - 反编译 `classes.dex`，直接读 `SspPacket` / `SspReader` / `ConnectionManagerService`
    的 Java 逻辑，补齐上面第 1、5、7、10 项；
  - 用 `apktool` 还原完整 `AndroidManifest.xml` 与资源，核对组件声明。
- 对 `lib/arm64-v8a/libsmartfolder.so` 做 `strings` + `nm -D` / `otool`，确认
  `parseIoBuffer` 的调用关系与 AES 常量。
- 把 `main/proto/SmartSyncProtocol.proto` 用 `protoc` 生成一遍，核对字段号与默认值，
  形成可直接用于新项目的参考 schema（放在 `tmp/analysis/`）。
- 通读 `zh-Hans.lproj/Localizable.strings` 全部 850 行，把 UI 状态与错误文案整理成
  状态机/错误码对照表。

## 3. 动态验证计划（需要真实设备，暂不执行）

1. 准备一台安卓机与一台 Mac，安装两端应用，连到同一局域网。
2. 用 Wireshark / tcpdump 抓局域网流量，过滤 mDNS 与自定义 TCP 端口：
   - 确认 `_handshaker_ssp._tcp` 的 TXT 记录内容；
   - 确认 TCP 连接方向、是否有 TLS、帧头结构；
   - 触发一次小文件传输，观察 `session_id` 如何关联控制消息与裸流。
3. 分别走 USB-AOA 与 USB-ADB（开/关 USB 调试）两条路径，记录 `adb forward --list`
   与端口变化。
4. 生成并解码连接二维码，确认载荷格式。
5. 构造锁屏、拒绝信任、拔线、大文件中断等场景，核对 `result` 取值与错误码。

所有抓包与日志产物只写入 `tmp/analysis/`，不删除、不清理任何现有文件。

## 4. 给实现阶段的建议

- 在动手写新项目代码前，优先验证第 1、2、5、10 项，它们直接决定帧格式与传输层设计。
- 第 12 项（官方原版对照）若无法完成，就以本样本 + Mac 端 `SSP*` 类名双向印证为准，
  并在代码中把协议当作「自定义协议」而非「兼容 HandShaker」来实现，避免依赖未公开细节。
- 新项目不要以「兼容 HandShaker 协议」为目标（该协议闭源且含硬编码混淆），
  而是借鉴其**分层与状态机**，自定义一套干净协议，见 `05-同等策略的新项目设计.md`。
