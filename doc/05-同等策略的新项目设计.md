# 05 同等策略的新项目设计

> 目标：做一个与 HandShaker **同一策略**的「Android ↔ PC / Mac 文件与信息传输工具」。
> 「同等策略」指沿用其核心架构决策，而不是复刻代码或外观。

## 1. 可复用的核心策略

| HandShaker 的做法 | 为什么值得照搬 | 新项目取舍 |
| --- | --- | --- |
| 传输通道与业务协议彻底解耦 | USB / Wi-Fi 可插拔，上层逻辑只写一次 | **照搬**，作为第一原则 |
| 一套 `.proto` 双端生成代码 | 协议唯一真相，避免两端漂移 | **照搬** |
| Protobuf 控制面 + `session_id` 裸流数据面 | 大文件不进 `bytes` 字段，省内存、可流式、可取消 | **照搬** |
| 两轮握手 + 用户在手机端确认信任 | 无需账号即可建立可信配对 | **照搬**，但改用现代密钥交换 |
| 心跳 + 超时判定掉线 | 长连接可靠感知 | **照搬** |
| 电脑端把手机当「远程文件服务」 | 不依赖 MTP，能读媒体库、剪贴板、目录变更 | **照搬** |
| mDNS/Bonjour 自动发现 + 二维码兜底 | 跨网段/防火墙时仍可连 | **照搬** |
| USB-AOA 优先、ADB 转发兜底 | 免 USB 调试即可用 | **照搬**（最难的一块，放后期） |
| 要求手机安装「传输服务」APK、未知来源安装 | 现在体验差、风险高 | **不照搬**：改为让用户从应用商店/官网装独立 App，或做成免安装的 accessory 模式 |
| 云账户、统计上报、Sparkle 更新、闪念胶囊 | 与互传无关 | **剔除** |
| native 层硬编码 AES key 做混淆 | 不是真正的安全边界 | **不照搬**，见 §6 |

## 2. 总体架构

```
┌────────────────────── 桌面端 (macOS / Windows / Linux) ──────────────────────┐
│  UI 层       设备列表 / 文件浏览器 / 传输队列 / 剪贴板面板 / 设置              │
│  应用核心    设备管理器、任务调度、断点续传、本地快照与同步状态(DB)             │
│  协议核心 ◄───────────── 共享 proto 生成代码 ──────────────► 协议核心          │
│  传输层      mDNS 发现 · TCP/TLS 监听与连接 · libusb/AOA · adb forward          │
└──────────────────────────────────────────────────────────────────────────────┘
                                     ▲  SSP-like 协议
┌────────────────────────── Android 端 App ────────────────────────────────────┐
│  前台 Service / 前台通知：连接管理、NSD 注册、ServerSocket                      │
│  数据提供者：文件系统(Storage Access / 直接路径)、MediaStore、ClipboardManager  │
│  变更订阅：FileObserver / ContentObserver → 主动推送事件                        │
│  传输层      NSD · ServerSocket/TLS · UsbAccessory(AOA) · ADB forward 被转发端 │
└──────────────────────────────────────────────────────────────────────────────┘
```

**关键约束**：协议核心（`.proto` + 帧编解码 + 状态机 + 握手）做成一份语言无关的实现，
桌面端与安卓端都调用它，避免 HandShaker 时代 Objective-C / Java 两套手写代码可能漂移的问题。

## 3. 技术栈建议

推荐组合（跨平台、可维护、性能足够）：

- **协议与传输核心**：Rust（或 Go）。Rust 更适合同时产出桌面端动态库与 Android JNI `.so`，
  且能安全处理流式 IO 与并发；用 `prost`/`protobuf` 生成消息，`tokio` 做异步网络。
- **桌面 UI**：Tauri（Rust + Web 前端）或 Electron。Tauri 体积小、与 Rust 核心天然同语言；
  若需要原生 Finder 拖拽体验，可换成 Swift（macOS）+ Rust 核心，Windows 用 C#/WinUI 调同一核心。
- **Android**：Kotlin，前台 Service + `NsdManager` + `ServerSocket`，JNI 调 Rust 核心；
  AOA 用 `UsbAccessory` API。
- **服务发现**：桌面端用 Bonjour/mDNS（Avahi 兼容），Android 用 `NsdManager`，服务类型自定义
  （例如 `_handover._tcp`，不要沿用对方的 `_handshaker_ssp._tcp`）。
- **USB**：桌面端 `libusb`/rusb 实现 AOA 控制请求 + bulk 传输；ADB 通道可选内置 adb 或
  调用系统 adb。

保守替代方案：全用 Kotlin Multiplatform + Compose 共享协议层；或 Node.js/Electron 桌面 +
Java/Kotlin 安卓，用 protobuf 的 JS/Java 生成代码。

## 4. 协议设计（简化版「SSP-like」）

### 4.1 帧格式

```
┌──────────┬──────────┬────────────┬────────────┬───────────────────────┐
│ magic(4) │ ver(1)   │ flags(1)   │ session_id │ length(u32, big-endian)│
├──────────┴──────────┴────────────┴────────────┴───────────────────────┤
│ payload: Protobuf 控制消息  或  裸二进制文件块(由 flags 标记)             │
└───────────────────────────────────────────────────────────────────────┘
```

- `session_id` 关联请求/响应，也关联裸流数据块；`CANCEL` 按 session_id 取消任务。
- 控制消息永远 Protobuf；文件字节流永远裸流（对应 proto 注释里被注释掉的 Body 消息）。
- 大文件按 `range{offset,length}` 分块，支持断点续传；每块可选 `gzip`；完成后校验
  `md5`/`sha256`。

### 4.2 命令集（MVP 子集）

| 分组 | 命令 |
| --- | --- |
| 会话 | `HELLO` / `HELLO_ACK`（能力协商：协议版本、App 版本、最小对端版本、心跳超时）、`PAIR_REQUEST` / `PAIR_RESPONSE`、`QUIT`、`CANCEL` |
| 保活 | `HEARTBEAT` / `HEARTBEAT_ACK`（互报时间戳） |
| 设备 | `GET_DEVICE_INFO`（型号、电量、存储、根目录、系统版本、权限状态） |
| 文件 | `LIST_DIR`、`STAT`、`MKDIR`、`RENAME`、`DELETE`（含回收站语义）、`UPLOAD_INIT` / `UPLOAD_DATA` / `UPLOAD_DONE`、`DOWNLOAD_INIT` / `DOWNLOAD_DATA` / `DOWNLOAD_DONE` |
| 媒体 | `GET_MEDIA_LIB`、`GET_THUMBNAIL`、`MEDIA_LIB_CHANGE` |
| 剪贴板 | `GET_CLIPBOARD`、`POST_CLIPBOARD`、`CLEAR_CLIPBOARD`、`CLIPBOARD_CHANGE` |
| 监控 | `WATCH_DIR` / `UNWATCH_DIR`、`FILE_EVENT`、`SYNC_SNAPSHOT` / `SYNC_DELTA` |

错误码沿用统一枚举（权限、磁盘不足、校验失败、路径过长、目标已存在、已取消等），
便于 UI 直接映射提示。

### 4.3 握手与信任（现代化改造）

HandShaker 用 `enckey` + `derived_key` + `RSA_encrypt('ok')`，且把 AES 密钥硬编码在
native 层。新项目建议：

1. 双端各自生成长期 `Ed25519`/`X25519` 密钥对，首次配对时交换公钥。
2. 桌面端显示 6 位配对码（或二维码内含 IP:port + 临时公钥指纹），手机端输入/扫码确认。
3. 用 X25519 派生会话密钥，之后用 **TLS 1.3 或 AES-GCM/ChaCha20-Poly1305** 加密通道；
   证书可用自签 + 公钥固定（pinning），不依赖公网 CA。
4. 信任级别只保留「本次信任 / 始终信任 / 移除」三档，持久化设备指纹。
5. 锁屏/未授权时返回明确状态（`locked` / `need_auth`），桌面端给出对应引导文案。

这样既保留了「无需账号、用户在手机端确认」的体验，又避免硬编码密钥。

### 4.4 心跳与掉线

`HELLO` 时由主机下发 `heartbeat_timeout_second`；双端互发心跳，超时即清理会话、
取消未完成传输、通知 UI。ADB 通道额外需要保活以免 forward 被回收。

## 5. 三条通道的实现要点

| 通道 | 优先级 | 实现要点 | 主要风险 |
| --- | --- | --- | --- |
| Wi-Fi 局域网 | P0 | 手机端 `NsdManager` 注册 + `ServerSocket` 监听；桌面端 mDNS browse + resolve + TLS 连接；二维码兜底（IP:port + 指纹） | mDNS 被路由器/防火墙阻断、多网卡选路、Android 后台限制、Wi-Fi 需同网段 |
| USB-AOA | P2 | 桌面端 libusb 读 AOA 版本 → 发送 manufacturer/model/version 控制串 → `ACCESSORY_START` → bulk in/out；Android 用 `accessory_filter.xml` + `USB_ACCESSORY_ATTACHED` 自启服务 | 部分机型不支持 AOA、驱动/权限、与 MTP 冲突、AOA v1/v2 差异 |
| USB-ADB 转发 | P2 | `adb forward tcp:<local> tcp:<remote>` → 桌面端连 localhost；需检测 USB 调试授权 | 用户需开 USB 调试、各家系统弹窗不同、forward 保活 |

建议 **P0 只做 Wi-Fi**，把「插线更好用」作为后续增量，先验证协议与状态机是否成立。

## 6. 安全与隐私设计

- **不硬编码任何对称密钥**；密钥全部临时派生，长期身份密钥存在系统钥匙串/Keystore。
- 默认只在局域网通信，**不上传任何文件内容到云端**；不引入账户体系、遥测上报。
- 剪贴板同步是敏感能力：默认关闭，需用户在手机端单独授权，并在 UI 明示。
- 文件访问遵循最小权限：Android 优先用 scoped storage / SAF，避免申请
  `WRITE_MEDIA_STORAGE` 之类的系统级权限。
- 桌面端不监听公网地址，只绑定局域网接口 + 回环；连接需配对确认，避免被同网段其它设备接入。
- 传输校验用 SHA-256；提供取消、断点、覆盖确认、回收站语义。

## 7. MVP 分期

| 阶段 | 交付 |
| --- | --- |
| P0 | 共享 `.proto` + 帧编解码；Wi-Fi mDNS 发现；两轮握手与信任；心跳；`LIST_DIR` / `STAT` / 上传下载（分块 + 校验 + 取消）；桌面端最小文件浏览器与传输队列 |
| P1 | 剪贴板双向同步；目录监控与文件变更推送；缩略图；媒体库浏览；二维码兜底连接 |
| P2 | USB-AOA 通道；USB-ADB 转发通道；多通道自动切换与优先级策略 |
| P3 | 照片自动同步与快照增量；多设备管理；断点持久化；Finder/资源管理器集成；Windows 与 Linux 适配 |

## 8. 明确剔除的部分

云账户登录、统计/追踪上报、Sparkle 自动更新、闪念胶囊插件、讯飞语音、
无损音频播放插件、阿里云 OSS 反馈上传、以及要求「未知来源安装传输服务」的引导流程。
这些在 HandShaker 里都属于外围或历史包袱。

## 9. 风险清单

- Android 10+ 分区存储与后台启动限制，可能影响长期驻留的 ServerSocket 与 FileObserver。
- AOA 在部分厂商 ROM 上不可用；与 MTP/Android File Transfer 冲突需主动检测。
- 跨网段、企业 Wi-Fi、访客网络下 mDNS 不可用，二维码兜底必须做扎实。
- 大文件、大量小文件、中文/特殊字符路径、符号链接、权限边界，都是易错点。
- 两端协议版本兼容：必须在 `HELLO` 阶段就做版本协商与最小版本拒绝。
- 静态分析得出的帧格式与握手细节尚未经实机验证，实现前应先做一次抓包验证，见
  `06-待验证问题与后续分析计划.md`。
