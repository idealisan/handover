# 01 分析范围与方法

> 本系列报告分析 Smartisan HandShaker（锤子科技出品的手机与电脑互传工具）的工作原理，
> 目标是为一个采用相同策略的「Android ↔ PC / Mac 文件与信息传输工具」项目提供依据。

## 1. 分析目标

1. 弄清 HandShaker 在电脑端与手机端之间如何发现设备、建立连接、完成授权。
2. 弄清文件、媒体库、剪贴板等数据的传输协议与命令集。
3. 弄清 USB 与 Wi-Fi 两种链路各自的实现方式与适用条件。
4. 提炼可复用的策略，输出新项目的设计要点。

## 2. 样本

| 端 | 样本 | 版本 | 位置 |
| --- | --- | --- | --- |
| Mac/PC 端 | `HandShaker.app`（macOS 应用包，约 38 MB，x86_64） | 2.5.6（构建 408），签名时间 2018-03-29 | `tmp/HandShaker.app/` |
| Android 端 | 安卓 APK（约 6.5 MB，单 dex，含 7 个 ABI 的 native 库） | 2.5.5，`VERSION_CODE=401` | `tmp/` 目录下的 APK 文件 |
| Android 端（新增，官方） | 安卓 APK（约 5.5 MB，单 dex，含 7 个 ABI 的 native 库） | 1.1.0，`VERSION_CODE=182`，2017-05-03 | `tmp/HandShaker.apk` |

安卓端旧 APK 的包名为 `com.smartutils.smartfolder.airshare`，但内部代码包名仍是
`com.smartisanos.smartfolder`。它带有第三方广告 SDK、用户手册指向第三方站点，且构建时间为
2020 年，晚于 Mac 端样本。**因此它应被视为「与 SSP 协议兼容的第三方/重打包实现」，
而不是锤子官方原版手机端应用。** 本系列报告用它来还原安卓侧的协议行为，凡涉及官方实现
的细节均标注为推断，见 `06-待验证问题与后续分析计划.md`。

后续新增的官方样本鉴定、协议版本对照与对前序报告的修订，见
`07-官方HandShaker-APK对照分析.md`。

## 3. 分析方法

参考 `morluto/rea`（Reverse Engineer Anything）的分层思路：先清点安装目录与组件，
再从字符串、符号、元数据中提取事实，最后把事实组织成协议与行为模型，并明确每条结论的
证据与局限。

实际执行的层次：

1. **包结构清点**：`Info.plist`、entitlements、签名、Frameworks、PlugIns、XPCServices、
   LoginItems、资源 plist、nib、Localizable.strings。
2. **二进制静态分析**：`file` / `otool -L` / `strings` 提取类名、方法名、命令名、
   URL、端口、错误串；`plutil -p` 读取 plist；Python 解析二进制 AXML 的字符串池。
3. **协议还原**：APK 内直接附带了 `main/proto/SmartSyncProtocol.proto`，这是最权威的
   一手证据；Mac 端 `SmartFinderCore.framework` 中的 `SSP*` Objective-C 类名与该 proto
   逐条对应，构成双向印证。
4. **行为推断**：把「连接 → 握手 → 心跳 → 业务请求 → 文件流」串成时序，区分
   「有直接证据」与「基于命名和 UI 文案的推断」。

## 4. 证据等级约定

- **【事实】**：直接来自文件内容（proto 定义、plist 键值、类名、字符串常量）。
- **【强推断】**：多个独立证据指向同一结论（例如 Mac 端 `adb forward tcp:10086` 与
  APK 端 `ServerSocket` 同时出现）。
- **【推断】**：仅由命名、UI 文案或常识推出，尚未经运行时验证。
- **【未验证】**：需要抓包或动态调试才能确定，统一汇总在 `06-待验证问题与后续分析计划.md`。

## 5. 本次分析的边界

- 全程为**静态分析**：未运行 HandShaker，未启动 APK，未连接真实手机，未做网络抓包。
- 未使用反编译器（环境无 Hopper/Ghidra/IDA/jadx 等），因此没有汇编级、控制流级结论。
- 所有中间产物仅放在 `tmp/analysis/` 下，未在项目外创建文件，未删除或清理任何文件。
- 报告中一律使用项目内相对路径，不记录本机绝对路径、用户名等本地环境信息。

## 6. 结论速览

HandShaker 的核心策略可以概括成一句话：

> **把「传输通道」和「业务协议」彻底解耦。通道可以是 USB-AOA、USB-ADB 转发、或局域网
> TCP；无论走哪条通道，上面跑的都是同一套基于 Protobuf 的 SmartSync Protocol（SSP），
> 由它在双端之间维护设备发现、两轮握手与信任、心跳保活、以及文件/媒体库/剪贴板的
> 请求-响应模型。**

这也是新项目最值得照搬的一点：先定义稳定的协议与状态机，再插拔不同的物理链路。
